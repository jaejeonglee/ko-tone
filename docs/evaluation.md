# 평가 기록

ko-tone을 만들면서 다섯 번의 블라인드 비교를 했습니다. 이 문서는 무엇을, 어떻게 비교했고, 그 결과로 스킬의 범위를 어떻게 정했는지 정리한 것입니다.

## 방법

- **비교 대상:** 같은 요청을 ko-tone을 읽은 실행과 아무 스킬도 쓰지 않은 실행에 한 번씩 맡겼습니다. 두 실행 모두 같은 모델(Claude Opus 5.5)을 쓰는 Claude Code 서브에이전트이고, 서로의 결과나 채점 기준을 보지 못하게 했습니다.
- **사람 검토:** 원문, 후보 A, 후보 B를 나란히 놓은 페이지에서 저장소 작성자가 더 나은 쪽을 골랐습니다. A와 B의 순서는 사례마다 무작위로 정했고, 어느 쪽이 스킬인지와 변경 설명은 고른 뒤에 공개했습니다.
- **객관 채점:** 원문 사실(수치, 날짜, 주소, 코드)이 남았는지, 새로 생긴 숫자가 정확한 계산값인지, '날짜(요일)'가 맞는지, 금지 표현과 빈 자리 표시가 없는지를 스크립트로 채점했습니다.
- **평가 틀:** [oil-skill-creator](https://github.com/oil-oil/oil-skill-creator)의 평가 디렉터리 구조와 집계 스크립트를 썼습니다.

이 결과로 0.7.0부터 형식 문서는 스킬 범위에서 뺐습니다.

## 회차별로 배운 점

- **1회차:** 사실 보존과 '원문 존중' 규칙이 너무 강해서, 원문의 빈말("중요한 역할을 할 것으로 보입니다")까지 지키고 공지의 인사와 목록까지 지웠습니다. 결과가 짧고 밋밋했습니다.
- **2회차:** 빈말을 걷어내고 채널 관행을 따르게 고치자 슬랙 공지에서 이겼습니다. 블로그에서는 기능 목록을 불릿으로 쪼개고 결론 없이 끝내서 졌습니다.
- **3회차:** 스킬 없는 쪽은 맞는 계산값(증감률, 요일, UTC→KST 변환)과 이메일 호칭·서명 자리를 스스로 덧붙였고, 사람은 그쪽을 골랐습니다. 스킬의 "원문에 없는 숫자 금지" 규칙이 이런 도움을 막았습니다.
- **4회차:** 계산 스크립트로 보강하게 했지만, 스킬 없는 쪽도 EIP-55 체크섬 오류를 잡고 시간대를 정확히 바꿨습니다. 스킬 쪽은 빈 자리 표시(`[배포일]`)와 중복으로 덜 완성돼 보였습니다.
- **5회차:** 빈 자리 표시와 중복, 과한 보강을 줄였지만 형식 문서에서는 여전히 졌습니다. 어조가 중요한 투자자 메일에서는 이겼습니다.

## 객관 채점과 비용

- 객관 기준 통과율은 대부분 회차에서 스킬 쪽이 같거나 조금 높았습니다. 스킬 없는 쪽은 사실을 바꾸는 일이 몇 번 있었습니다(`EIP-4337` → `ERC-4337`, README 코드 블록 주석 수정, `[링크]` 같은 빈 칸).
- 시간과 토큰은 스킬 쪽이 늘 더 들었습니다. 5회차 기준으로 사례당 평균 118초 대 52초, 토큰 약 8.9만 대 6.7만입니다. 지시문과 참고 자료를 읽고 스크립트를 돌리는 비용입니다. 0.7.0은 스크립트를 필요할 때만 쓰게 바꿨지만, 바꾼 뒤의 비용은 다시 재지 않았습니다.

## 한계

- 사례마다 설정별로 한 번씩만 실행했습니다. 같은 요청도 실행마다 결과가 달라지므로 경향으로만 봐야 합니다.
- 사람 검토자는 한 명(저장소 작성자)입니다.
- 1회차의 두 사례는 검토 전에 결과 일부가 검토자에게 알려져 완전한 블라인드가 아니었습니다.
- 0.4.0 이후 어조·문장 쪽 3승은 표본이 작습니다. 0.7.0 자체는 블라인드 비교를 하지 않았고, 호출 범위만 확인했습니다(블로그 회고 다듬기 요청은 호출됨, 회의록 정리 요청은 호출되지 않음).

평가 사례는 `skills/ko-tone/evals/evals.json`에 모두 남겨 두었습니다. 형식 문서 사례는 지금 범위 밖이지만, 다음 버전에서 다시 비교할 때 쓸 수 있습니다.
